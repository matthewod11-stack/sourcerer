# Phase 6 Spike: Batch Scoring

## Summary

Phase 6 adds an experimental batch-scoring path that can score the E-1 golden set in one structured-output call, compare it against the existing per-candidate baseline, and write JSON/Markdown A/B reports.

Implemented commands:

```bash
sourcerer score --batch --mock
sourcerer score --batch --model claude-opus-4-7
sourcerer eval --batch --mock
```

`--mock` uses deterministic fixture providers and spends no API quota. Live runs use the configured provider from `~/.sourcerer/config.yaml`; `sourcerer score --batch` defaults live runs to `claude-opus-4-7`.

## Design Notes

- Batch output is validated with a Zod schema before scoring.
- Evidence grounding is still checked per candidate, so a batch output cannot cite another candidate's evidence without being penalized and stripped by the existing H-9 grounding path.
- The batch prompt requests both per-candidate signals and an overall relative ranking. The ranking is reported, but tier metrics are still computed from the same local score calculator as the baseline.
- Cost is computed from the single batch call's token usage and allocated evenly across candidates for report aggregation.
- The prompt lives in `packages/ai/prompts/scoring-batch.md` and is versioned through the E-4 prompt registry.

## Recommendation

Go for continued experimentation; no-go for making batch scoring the default yet.

The hardening pass goal is met because Phase 6 now has a real, repeatable measurement harness and an experimental CLI path. The next product decision should be based on a deliberate live run with provider quota approved:

```bash
sourcerer score --batch --model claude-opus-4-7 --output-dir eval-results/phase-6-live
```

Promote batch scoring only if the live run improves tier accuracy or candidate ordering enough to justify higher model cost and larger prompt surface. Until then, keep per-candidate scoring as the production default and treat batch scoring as an eval-backed experiment.
